# 详细设计发布到飞书

> 将详细设计（LLD）发布到飞书云文档，供高级开发/模块负责人审阅确认。确认通过后进入实现计划阶段，否则回退修改。

## 触发场景

- 详细设计（LLD）通过一致性审查（consistency-review-2）后

## 输入

| 制品 | 路径 | 必须 |
|------|------|------|
| 详细设计 | `docs/artifacts/lld.md` | 是 |
| 飞书文档链接记录 | `docs/artifacts/feishu-doc-links.md` | 否（重新发布时读取） |

## 执行步骤

### 1. 读取本地制品

读取 `docs/artifacts/lld.md`，确认文件存在且内容完整。

### 2. 发布到飞书云文档

使用飞书文档 API（lark-cli）执行：

- **首次发布**：在指定文件夹下创建飞书文档，将 Markdown 内容写入，记录文档 URL 到 `docs/artifacts/feishu-doc-links.md`
- **修改后重新发布**：读取 `feishu-doc-links.md` 获取已有文档 URL，覆盖更新文档内容，在文档末尾追加修改说明（轮次、修改摘要）

### 3. 展示审阅检查清单

向用户展示飞书文档链接，并附上以下 LLD 审阅检查清单，提醒审阅关注点：

#### LLD 审阅检查清单

- [ ] **类设计对应**：LLD 中的类/接口是否与 HLD 模块一一对应或合理派生
- [ ] **DDL-Entity 对齐**：实体类字段是否与 DDL 表结构匹配（名称、类型、可空性）
- [ ] **API-Controller 对齐**：Controller 方法签名是否与 API 契约一致（路径、参数、响应体、状态码）
- [ ] **方法签名完整**：每个公共方法是否包含参数类型、返回值、异常声明
- [ ] **业务流程**：核心业务的序列图/调用链是否完整覆盖正常和异常路径
- [ ] **异常处理策略**：各层异常捕获和转换规则是否清晰、是否覆盖 API 错误码
- [ ] **数据映射**：Entity / DTO / VO 之间的转换关系是否明确、敏感字段是否排除

### 4. 等待人工确认

```
提示: "详细设计已发布到飞书，请审阅后确认:
  - 确认通过 → 回复'确认'，进入实现计划阶段
  - 需要修改 → 回复修改意见，将回退给详细设计代理修正"
```

暂停流程，等待用户响应。

### 5. 处理用户响应

| 响应类型 | 处理方式 |
|---------|---------|
| 确认通过 | 记录到 `decision-log.md`，继续进入实现计划 |
| 需要修改 | 将修改意见回退给 `lld-author` 修正，修正后重新执行本技能 |
| 部分确认 | 记录已确认部分 + 待修改部分，回退修改 |

## 输出

| 产出 | 路径 | 说明 |
|------|------|------|
| 飞书文档链接记录 | `docs/artifacts/feishu-doc-links.md` | 存储 LLD 飞书文档 URL |
| 决策记录 | `docs/artifacts/decision-log.md` | 追加人工审阅结论 |
| harness 日志 | `docs/artifacts/harness-debug.md` | 记录发布和确认事件 |

## 约束

- 发布前必须确认 LLD 一致性审查已通过
- 飞书文档链接必须持久化到 `feishu-doc-links.md`，支持后续更新
- 人工确认为阻塞操作，未确认前不得进入实现计划
- 修改回退后重新发布时更新同一文档，不创建新文档
- 每次发布和确认事件都写入 `harness-debug.md`
