# 需求方案头脑风暴

> 结构化探索需求的多种实现方案，避免拿到需求就直接写代码。

## 触发场景

- 拿到新 PRD 或新需求，尚未确定技术方案
- 功能交付工作流的设计阶段前
- 用户明确要求"讨论一下方案"

## 前置条件

- `{artifact_root}/analysis/feature-list.md` 已存在（由 `requirements-analyst` 产出）
- 如不存在，停止执行并报告缺失

## 执行步骤

### 第一步：梳理边界

从 `feature-list.md` 中提取关键约束：

1. **功能边界**：哪些是本次必须做的？哪些是明确不做的？
2. **技术约束**：现有技术栈、框架版本、基础设施限制
3. **非功能约束**：性能要求、并发量、数据量级、安全合规要求
4. **时间约束**：工期限制是否影响方案选择
5. **集成约束**：需要对接的外部系统或已有模块

输出格式：

```markdown
## 约束清单
- 必须做：[列表]
- 明确不做：[列表]
- 技术约束：[列表]
- 非功能约束：[列表]
- 时间约束：[描述]
- 集成约束：[列表]
```

### 第二步：列举方案

至少列出 2-3 种不同的技术方案，每种方案包含：

1. **方案名称**：简短标识（如"方案 A：Spring Security + JWT"）
2. **核心思路**：一句话概述技术选型和架构方式
3. **关键设计**：主要的技术选型、数据存储方式、接口设计思路
4. **实现要点**：需要注意的技术难点和解决思路

### 第三步：对比优劣

构建对比矩阵：

```markdown
## 方案对比

| 维度 | 方案 A | 方案 B | 方案 C |
|------|--------|--------|--------|
| 实现复杂度 | 低/中/高 | ... | ... |
| 性能表现 | ... | ... | ... |
| 可维护性 | ... | ... | ... |
| 可扩展性 | ... | ... | ... |
| 开发工期 | ... | ... | ... |
| 技术风险 | ... | ... | ... |
| 与现有系统兼容性 | ... | ... | ... |
```

### 第四步：输出推荐

将完整分析结果写入 `{artifact_root}/design/brainstorm-result.md`：

```markdown
# 需求方案头脑风暴

## 需求概要
[从 feature-list.md 中提炼的一句话需求描述]

## 约束清单
[第一步的输出]

## 方案列表

### 方案 A：[名称]
- 核心思路：...
- 关键设计：...
- 实现要点：...

### 方案 B：[名称]
- 核心思路：...
- 关键设计：...
- 实现要点：...

### 方案 C：[名称]（可选）
- ...

## 方案对比
[第三步的对比矩阵]

## 推荐方案
- 推荐：方案 [X]
- 理由：[具体的推荐原因，引用对比矩阵中的关键优势]
- 风险：[推荐方案的主要风险和缓解措施]

## 待确认事项
- [需要用户确认的技术决策点]
- [需要用户补充的需求细节]
```

## 约束

- 本技能为分析与讨论，不产出设计文档或代码
- 必须列出至少 2 种方案，不能只给一种
- 推荐方案必须基于对比分析，不能凭直觉
- 如果存在需要用户确认的关键决策点，必须在"待确认事项"中列出
- 输出文件路径固定为 `{artifact_root}/design/brainstorm-result.md`
