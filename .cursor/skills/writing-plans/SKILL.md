# 设计转实现计划

> 将概要设计（HLD）和详细设计（LLD）转化为可执行的子任务清单，让 implementer 可以直接上手。

## 触发场景

- LLD 设计完成后，进入实现准备阶段
- 功能交付工作流的"实现计划"步骤

## 前置条件

- `docs/artifacts/lld.md` 必须存在（由 `lld-author` 产出）
- `docs/artifacts/hld.md` 建议存在（参考用）
- 如果 `lld.md` 不存在，停止执行并报告缺失

## 执行步骤

### 第一步：拆分子任务

从 `lld.md` 中提取所有需要实现的类、方法、配置，按以下粒度拆分：

**拆分原则**：
- 每个子任务对应**一个可独立验证的变更**
- 每个子任务的实现时间不超过 1 小时
- 每个子任务有明确的完成判定标准

**典型子任务类型**：

| 类型 | 示例 | 粒度 |
|------|------|------|
| Entity 创建 | 创建 `User` 实体类 | 一个实体 = 一个任务 |
| Repository 层 | 创建 `UserRepository` 接口 | 一个接口 = 一个任务 |
| Service 层 | 实现 `UserService.register()` | 一个核心方法 = 一个任务 |
| Controller 层 | 实现 `POST /api/users` | 一个端点 = 一个任务 |
| 配置文件 | 添加数据源配置 | 一组相关配置 = 一个任务 |
| 测试 | `UserServiceTest` | 一个测试类 = 一个任务 |
| DDL 执行 | 执行建表 SQL | 一批相关表 = 一个任务 |

### 第二步：标注依赖

为每个子任务标注：

1. **前置依赖**：必须先完成哪些子任务
2. **软依赖**：最好先完成但不阻塞
3. **无依赖**：可独立开始

依赖关系用有向图表示：

```markdown
## 依赖关系
- T1 (Entity) → T3 (Repository) → T5 (Service)
- T2 (DDL) → T3 (Repository)
- T4 (Config) → T5 (Service)
- T6 (Controller) 依赖 T5 (Service)
- T7 (Test) 可与 T6 并行
```

### 第三步：判定并行度

基于依赖关系图，识别可并行执行的任务组：

```markdown
## 并行策略
- 第一波（无依赖）：T1, T2, T4 可并行
- 第二波（依赖第一波）：T3 可开始
- 第三波（依赖第二波）：T5, T7 可并行
- 第四波（依赖第三波）：T6
```

如果并行度 ≥ 2，标注"建议使用 Git Worktree 并行开发"。

### 第四步：定义验证方式

每个子任务必须有可执行的验证标准。涉及单元测试/Service 变更时，**按项目 JaCoCo 接入状态选择命令**（与 test-guard 门禁一致）：

| JaCoCo 状态 | 模块级命令 | 全量命令 |
|---|---|---|
| 已接入 check（`pom.xml` 含 `jacoco-maven-plugin` 的 `check` goal） | `mvn verify -pl <module> -am -q` | `mvn verify -q` |
| 未接入或仅 report | `mvn test -pl <module> -am -q` | `mvn test -q` |

| 验证类型 | 适用场景 | 示例 |
|----------|----------|------|
| 编译通过 | 所有任务 | `mvn compile -q` 成功 |
| 单元测试 | Service / 测试类 | 上表模块级命令通过 |
| 集成测试 | Controller/API | HTTP 请求返回预期响应 |
| DDL 验证 | 数据库变更 | 表结构与 ddl.md 一致 |
| Lint 检查 | 所有代码任务 | 无新增 lint 错误 |

### 第五步：输出实现计划

将完整计划写入 `docs/artifacts/impl-plan.md`：

```markdown
# 实现计划

## 概要
- 来源设计：docs/artifacts/lld.md
- 总任务数：N
- 预计并行度：M
- 关键路径：T1 → T3 → T5 → T6

## 子任务清单

| ID | 任务描述 | 类型 | 目标文件 | 依赖 | 验证方式 | 预计工时 |
|----|----------|------|----------|------|----------|----------|
| T1 | 创建 User 实体 | Entity | src/.../User.java | 无 | 编译通过 | 15min |
| T2 | 执行建表 DDL | DDL | sql/V1__create_user.sql | 无 | 表结构验证 | 10min |
| ... | ... | ... | ... | ... | ... | ... |

## 依赖关系图
[第二步的输出]

## 并行策略
[第三步的输出]

## 执行顺序（推荐）
1. 第一波：T1, T2, T4（并行）
2. 第二波：T3
3. ...

## 风险与注意事项
- [需要注意的技术点]
- [可能阻塞的外部依赖]
```

## 约束

- 本技能为计划编排，不执行实际编码
- 每个子任务必须可追溯到 `lld.md` 中的具体类或方法
- 输出文件路径固定为 `docs/artifacts/impl-plan.md`
- 禁止出现无法验证的子任务（"优化代码结构"这种不算）
- 如果 LLD 中有遗漏或不清楚的设计，标注为风险而非自行补充
