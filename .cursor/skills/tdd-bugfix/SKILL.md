# 测试驱动修复（Test-Driven Bugfix）

> 本技能定义了以测试为驱动的 Bug 修复流程。核心原则：**先写失败测试证明 Bug 存在，再写最小修复让测试通过**。

## 适用场景

- 根因已确认，进入修复阶段
- 需要保证修复的正确性和不引入回归

## 前置条件

- 已完成根因分析，`docs/artifacts/root-cause.md` 存在且内容完整
- 根因报告中明确了：根因位置（类名/方法名/行号）、触发条件、建议修复方向
- 项目的测试框架可正常运行（JUnit / TestNG 等）

---

## 步骤 1：编写失败测试

**目标**：用测试代码精确描述 Bug 的触发条件和错误行为，测试必须在修复前失败。

### 执行流程

1. **阅读根因分析报告**：从 `docs/artifacts/root-cause.md` 获取根因位置、触发条件、预期行为和实际行为
2. **确定测试位置**：在对应模块的 `src/test/java` 目录下，找到或创建对应的测试类
3. **编写测试用例**：

```java
@Test
@DisplayName("修复: [Bug 简述] - [触发条件描述]")
void should_[预期行为]_when_[触发条件]() {
    // Given - 构造触发 Bug 的输入条件
    // When  - 执行触发 Bug 的操作
    // Then  - 断言期望的正确行为（当前应该失败）
}
```

4. **运行测试，确认失败**：测试必须因为 Bug 本身而失败，而非因为测试代码有误

### 测试设计原则

| 原则 | 说明 |
|------|------|
| **精准触发** | 测试输入必须精确命中根因描述的触发条件，不能用宽泛的输入碰运气 |
| **单一断言** | 每个测试用例只验证一个行为点，避免多个断言混淆失败原因 |
| **边界覆盖** | 除核心触发条件外，补充边界值测试（null、空集合、最大值等） |
| **命名清晰** | 测试方法名和 `@DisplayName` 要准确描述场景，方便回归时理解 |
| **独立可重复** | 测试不依赖外部状态、执行顺序或其他测试的结果 |

### 验证检查点

- [ ] 测试运行后确实失败（红色）
- [ ] 失败原因与 Bug 现象一致（而非 NullPointerException 等测试代码本身问题）
- [ ] 测试覆盖了根因报告中描述的核心触发条件
- [ ] 补充了合理的边界条件测试

---

## 步骤 2：实施最小修复

**目标**：以最小改动让失败测试变为通过，不做任何超出修复范围的改动。

### 执行流程

1. **定位修改点**：根据根因报告直接定位到具体类和方法
2. **设计修复方案**：在改代码前，先明确写下修改什么、为什么这样改
3. **实施修改**：只修改导致 Bug 的代码，保持改动最小化
4. **运行目标测试**：确认步骤 1 中的失败测试现在通过

### 最小修复原则

| 原则 | 说明 |
|------|------|
| **只改根因** | 修改必须直接针对根因分析确认的代码位置，不顺手改其他的 |
| **最小改动** | 在多个修复方案中选择改动量最小、影响范围最小的方案 |
| **保持一致** | 修复代码的风格必须与周围代码一致（命名、格式、模式） |
| **保留语义** | 修复不应改变方法签名、返回值语义等公共契约，除非根因正是契约定义错误 |

### 验证检查点

- [ ] 步骤 1 的失败测试现在全部通过（绿色）
- [ ] 修改的文件数和行数是最小必要集
- [ ] `git diff` 中每一行改动都能用根因直接解释

---

## 步骤 3：运行全量回归测试

**目标**：确认修复没有引入副作用，已有功能不受影响。

### 测试命令（与 test-guard 门禁一致）

| JaCoCo 状态 | 模块级 | 全量 |
|---|---|---|
| 已接入 check（`pom.xml` 含 `jacoco-maven-plugin` 的 `check` goal） | `mvn verify -pl <module> -am -q` | `mvn verify -q` |
| 未接入或仅 report | `mvn test -pl <module> -am -q` | `mvn test -q` |

已接入 JaCoCo check 时**禁止**仅用 `mvn test` 代替 `mvn verify`。

### 执行流程

1. **运行所在模块的全量测试**：

```bash
# Maven — 已接入 JaCoCo check
mvn verify -pl <module-name> -am -q

# Maven — 未接入 JaCoCo
mvn test -pl <module-name> -am -q

# Gradle 项目
gradle :module-name:test
```

2. **运行项目全量测试**（模块测试通过后）：

```bash
# Maven — 已接入 JaCoCo check
mvn verify -q

# Maven — 未接入 JaCoCo
mvn test -q

# Gradle
gradle test
```

3. **分析失败测试**（如有）：
   - 如果新增失败与本次修复相关 → 修复引入了回归，回到步骤 2 调整修复方案
   - 如果新增失败与修复无关 → 记录为已知问题，不在本次修复范围内处理
   - 如果是已有的 flaky test → 记录，不阻塞本次修复

### 验证检查点

- [ ] 模块测试全部通过（已接入 JaCoCo 时使用 `mvn verify`）
- [ ] 项目全量测试通过（或失败项与本次修复无关）
- [ ] 没有新增的测试失败
- [ ] 已接入 JaCoCo check 时，覆盖率不低于基线（行 ≥ 78%，分支 ≥ 65%）

---

## 步骤 4：审视修复代码质量

**目标**：确认修复代码本身没有引入新的代码坏味道或潜在问题。

### 审查清单

| 检查项 | 描述 |
|--------|------|
| **异常处理** | 是否正确处理了异常？是否吞掉了不该吞的异常？ |
| **空值安全** | 新增/修改的代码路径是否有空指针风险？ |
| **资源管理** | 是否有未关闭的资源（流、连接、锁等）？ |
| **线程安全** | 修复是否涉及共享状态？并发场景下是否安全？ |
| **日志记录** | 关键路径是否有适当的日志？日志级别是否合理？ |
| **硬编码** | 是否引入了魔法数字、硬编码字符串等？ |
| **重复代码** | 修复逻辑是否与已有代码重复？是否需要抽取公共方法？ |
| **性能影响** | 修复是否引入了不必要的循环、查询或计算？ |

### 执行要求

- 对照上述清单逐项检查，不可跳过
- 如发现坏味道但不影响正确性，记录为 TODO 留待后续处理，本次不改
- 如发现坏味道且影响正确性或可维护性严重，在不超出修复范围的前提下一并修复

## 禁止事项

> 以下行为严格禁止，违反将导致工作流回退。

| 禁止行为 | 原因 |
|---------|------|
| **不写测试直接修复** | 无法证明修复的正确性，无法防止未来回归 |
| **修复范围超出根因** | 超范围改动增加风险，且无法通过根因分析解释其必要性 |
| **测试写在修复之后** | 先修复后补测试可能导致测试只验证了当前行为而非正确行为 |
| **忽略回归测试失败** | 任何与修复相关的测试失败都必须解决，不能跳过 |
| **修改测试让其通过** | 如果测试断言的是正确行为，不能因为代码不符合就改测试 |
| **一次提交混入无关改动** | 修复提交必须只包含修复相关代码和测试，便于回溯和 Cherry-pick |
