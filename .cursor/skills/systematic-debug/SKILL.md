# 结构化调试流程（Systematic Debugging）

> 本技能定义了从 Bug 报告到根因确认的完整调试流程。所有调试活动必须按步骤执行，严禁跳步。

## 适用场景

- 收到 Bug 报告需要复现和定位
- 生产环境异常需要根因分析
- 测试失败需要排查原因

## 前置条件

- 已获取 Bug 描述（至少包含：现象、期望行为、实际行为）
- 有权访问相关日志和代码仓库
- 本地开发环境可运行项目

---

## 步骤 1：收集信息

**目标**：建立对 Bug 的全面认知，避免信息缺失导致方向偏差。

### 必须收集的信息

| 类别 | 具体内容 | 获取方式 |
|------|---------|---------|
| **错误日志** | 完整的异常堆栈、错误码、错误消息 | 应用日志文件、控制台输出、日志平台 |
| **复现步骤** | 触发 Bug 的精确操作序列 | Bug 报告、与报告人确认 |
| **环境信息** | JDK 版本、框架版本、OS、数据库版本 | 运行环境配置文件、CI 构建信息 |
| **输入数据** | 触发问题的请求参数、数据库状态、配置值 | 请求日志、数据库查询 |
| **时间线** | Bug 首次出现时间、是否新引入、关联的最近变更 | Git log、部署记录 |

### 执行要求

1. 将堆栈信息完整复制，不要截断——根因往往藏在 `Caused by` 链的最末端
2. 确认 Bug 的可复现性：必现 / 偶现 / 特定条件下复现
3. 如果是偶现 Bug，记录已知的触发条件和未触发的条件
4. 将所有收集到的信息整理成结构化文档，作为后续分析的输入

---

## 步骤 2：形成假设列表

**目标**：基于收集到的信息，列出至少 3 个可能的根因假设，按可能性排序。

### 假设生成策略

1. **从堆栈出发**：异常抛出点 → 调用链上游 → 数据来源，逐层追溯
2. **从变更出发**：检查 Bug 首次出现前后的 Git 提交，重点关注相关模块的变更
3. **从数据出发**：检查输入数据是否存在边界值、空值、非法格式等异常情况
4. **从环境出发**：配置差异、依赖版本不兼容、资源不足（连接池耗尽、内存溢出等）
5. **从并发出发**：是否存在竞态条件、死锁、线程安全问题

### 输出格式

```markdown
## 假设列表

| # | 假设描述 | 可能性 | 验证方法 | 状态 |
|---|---------|--------|---------|------|
| 1 | [具体假设] | 高/中/低 | [如何验证] | 待验证 |
| 2 | [具体假设] | 高/中/低 | [如何验证] | 待验证 |
| 3 | [具体假设] | 高/中/低 | [如何验证] | 待验证 |
```

### 执行要求

- 假设必须是**具体的、可验证的**，而非模糊的方向（"可能是并发问题"不合格，"在 OrderService.createOrder() 中 inventory 扣减和订单创建未在同一事务中导致并发时库存不一致"合格）
- 每个假设必须附带验证方法
- 按可能性从高到低排序，优先验证高可能性假设

---

## 步骤 3：验证假设

**目标**：逐个验证假设，用证据排除或确认每个假设。

### 验证技术

| 技术 | 适用场景 | 操作方式 |
|------|---------|---------|
| **二分法定位** | 不确定问题引入的具体提交 | `git bisect` 在已知好/坏版本之间二分查找 |
| **断点调试** | 需要观察运行时变量状态 | 在关键路径设断点，检查变量值和执行流 |
| **日志插桩** | 偶现问题或异步流程难以断点 | 在可疑位置添加临时日志，记录关键变量值和执行路径 |
| **最小复现** | 复现步骤过长或依赖过多 | 剥离无关逻辑，构造最小化的测试用例复现问题 |
| **对比分析** | 同一逻辑在不同条件下表现不同 | 对比正常/异常情况下的输入、中间状态、输出差异 |
| **代码审查** | 逻辑错误、边界处理缺失 | 逐行阅读可疑代码路径，关注边界条件和异常处理 |

### 验证流程

```
选取可能性最高的假设
    ↓
设计验证实验（明确预期结果）
    ↓
执行验证
    ↓
┌─ 假设成立 → 进入步骤 4 确认根因
└─ 假设不成立 → 更新假设状态为"已排除"，选取下一个假设
    ↓
所有假设均排除 → 回到步骤 2，补充新假设
```

### 执行要求

- 每次只验证一个假设，不要并行验证多个
- 验证前明确写下"如果假设成立，预期会看到什么"
- 验证后记录实际结果，与预期对比
- 临时添加的日志/代码必须标记 `// TODO: debug - remove after fix`

---

## 步骤 4：确认根因

**目标**：排除其他可能性，锁定具体代码位置和触发条件。

### 确认标准

根因分析结论必须同时满足以下条件：

1. **可解释现象**：能完整解释 Bug 的所有已知表现（不只是部分）
2. **可定位代码**：精确到具体类、方法、行号
3. **可复现验证**：基于根因构造的测试用例能稳定复现问题
4. **可排除替代**：其他假设已被逐一排除，有证据记录

### 确认流程

1. 用一句话陈述根因：`[具体类.方法()] 在 [什么条件下] 因为 [什么原因] 导致了 [什么结果]`
2. 回顾所有已知现象，确认根因能解释每一个
3. 构造针对性的测试用例，验证修复此处后问题消失
4. 检查同一模式是否在代码库中还有其他位置出现

---

## 步骤 5：输出根因分析报告

**目标**：将分析过程和结论输出为结构化文档，供后续修复和回顾使用。

### 输出路径

`docs/artifacts/root-cause.md`

### 报告模板

```markdown
# 根因分析报告

## Bug 概述
- **问题描述**：[一句话描述]
- **影响范围**：[影响的功能/用户/数据]
- **严重程度**：Critical / Major / Minor
- **复现条件**：[精确的复现步骤]

## 分析过程

### 收集到的关键信息
- 异常堆栈：[粘贴或引用]
- 关键日志：[粘贴或引用]
- 环境信息：[版本、配置等]

### 假设与验证

| # | 假设 | 验证方法 | 结果 | 结论 |
|---|------|---------|------|------|
| 1 | ... | ... | ... | 已排除/已确认 |

## 根因结论

- **根因位置**：`[类名.方法名()]`（[文件路径]:[行号]）
- **根因描述**：[详细描述为什么会出错]
- **触发条件**：[什么情况下触发]

## 建议修复方向
- [修复方案简述]
- [需要注意的风险点]
- [是否需要同步修复其他位置]

## 影响评估
- [修复是否可能引入副作用]
- [需要哪些回归测试覆盖]
```

## 禁止事项

> 以下行为严格禁止，违反将导致工作流回退。

| 禁止行为 | 原因 |
|---------|------|
| **未分析就直接改代码** | 可能修错位置，引入新 Bug，浪费时间 |
| **同时改多处碰运气** | 无法确认真正的根因，即使表面修好也可能遗留隐患 |
| **跳过假设验证直接下结论** | 没有证据支撑的结论不可靠，可能导致错误修复 |
| **忽略偶现 Bug 的复现条件分析** | 偶现 Bug 通常涉及并发、时序等深层问题，不分析会反复出现 |
| **删除或注释掉出错代码了事** | 治标不治本，可能破坏功能完整性 |
| **不记录分析过程** | 失去知识积累，同类问题无法复用分析经验 |
