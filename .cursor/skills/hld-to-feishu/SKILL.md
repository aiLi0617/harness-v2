# 概要设计发布到飞书

> 将概要设计（HLD）发布到飞书云文档，供架构师/技术负责人审阅确认。确认通过后进入 DDL/API 设计阶段，否则回退修改。

## 触发场景

- 概要设计（HLD）通过一致性审查（consistency-review-1）后

## 输入

| 制品 | 路径 | 必须 |
|------|------|------|
| 概要设计 | `docs/artifacts/hld.md` | 是 |
| 飞书文档链接记录 | `docs/artifacts/feishu-doc-links.md` | 否（重新发布时读取） |

## 执行步骤

### 1. 读取本地制品

读取 `docs/artifacts/hld.md`，确认文件存在且内容完整。

### 2. 发布到飞书云文档

使用飞书文档 API（lark-cli）执行：

- **首次发布**：在指定文件夹下创建飞书文档，将 Markdown 内容写入，记录文档 URL 到 `docs/artifacts/feishu-doc-links.md`
- **修改后重新发布**：读取 `feishu-doc-links.md` 获取已有文档 URL，覆盖更新文档内容，在文档末尾追加修改说明（轮次、修改摘要）

### 3. 展示审阅检查清单

向用户展示飞书文档链接，并附上以下 HLD 审阅检查清单，提醒审阅关注点：

#### HLD 审阅检查清单

- [ ] **功能覆盖**：功能清单中的每个功能点是否都映射到了具体模块
- [ ] **模块边界**：每个模块职责是否单一、边界是否清晰（"不做的事"是否明确）
- [ ] **接口概览**：模块间接口是否完整（提供方、消费方、调用方式）
- [ ] **数据流**：请求从入口到存储的完整路径是否合理、有无瓶颈
- [ ] **技术选型**：关键技术组件选型是否有依据、是否与团队技术栈匹配
- [ ] **非功能需求**：性能指标、安全要求、可用性 SLA 是否可量化
- [ ] **无过度设计**：是否存在功能清单未提及的多余模块或过早优化

### 4. 等待人工确认

```
提示: "概要设计已发布到飞书，请审阅后确认:
  - 确认通过 → 回复'确认'，进入 DDL/API 设计阶段
  - 需要修改 → 回复修改意见，将回退给概要设计代理修正"
```

暂停流程，等待用户响应。

### 5. 处理用户响应

| 响应类型 | 处理方式 |
|---------|---------|
| 确认通过 | 记录到 `decision-log.md`，继续进入 DDL/API 设计 |
| 需要修改 | 将修改意见回退给 `architect-hld` 修正，修正后重新执行本技能 |
| 部分确认 | 记录已确认部分 + 待修改部分，回退修改 |

## 输出

| 产出 | 路径 | 说明 |
|------|------|------|
| 飞书文档链接记录 | `docs/artifacts/feishu-doc-links.md` | 存储 HLD 飞书文档 URL |
| 决策记录 | `docs/artifacts/decision-log.md` | 追加人工审阅结论 |
| harness 日志 | `docs/artifacts/harness-debug.md` | 记录发布和确认事件 |

## 约束

- 发布前必须确认 HLD 一致性审查已通过
- 飞书文档链接必须持久化到 `feishu-doc-links.md`，支持后续更新
- 人工确认为阻塞操作，未确认前不得进入 DDL/API 设计
- 修改回退后重新发布时更新同一文档，不创建新文档
- 每次发布和确认事件都写入 `harness-debug.md`
