# 重构方案规划

> 将模糊的"这段代码需要重构"转化为有序的、安全的、可验证的重构步骤序列。

## 触发场景

- 收到明确的重构需求
- 在开发过程中识别出代码坏味道
- 代码审查中发现结构性问题需要系统性改善

## 执行步骤

### 第一步：识别坏味道

逐一扫描目标代码，标注以下坏味道类型：

| 坏味道 | 识别信号 |
|--------|----------|
| 过长方法 | 方法超过 30 行，或需要滚动才能看全 |
| 重复代码 | 两处以上相似逻辑（结构相同、仅参数不同） |
| 上帝类 | 类职责超过 3 个，或字段/方法数量过多 |
| 特性依恋 | 方法大量使用另一个类的字段/方法，而非自身的 |
| 数据泥团 | 多个参数总是一起出现，应封装为对象 |
| 过长参数列表 | 方法参数超过 4 个 |
| 发散式变化 | 一个类因多种原因被频繁修改 |
| 霰弹式修改 | 一个变更需要修改多个类 |
| 中间人 | 类的大部分方法都委托给另一个类 |
| 拒绝继承 | 子类不使用父类的大部分方法/字段 |

输出格式：

```markdown
### 坏味道清单

1. **[坏味道类型]** — `类名.方法名`（行号范围）
   - 现象：[具体描述]
   - 严重程度：高/中/低
```

### 第二步：选择重构手法

为每个坏味道选择对应的重构手法：

| 坏味道 | 推荐手法 |
|--------|----------|
| 过长方法 | 提取方法（Extract Method） |
| 重复代码 | 提取方法 / 提取超类（Extract Superclass） |
| 上帝类 | 提取类（Extract Class） |
| 特性依恋 | 搬移方法（Move Method） |
| 数据泥团 | 引入参数对象（Introduce Parameter Object） |
| 过长参数列表 | 引入参数对象 / 以对象取代参数（Preserve Whole Object） |
| 发散式变化 | 提取类 |
| 霰弹式修改 | 内联类（Inline Class）/ 搬移方法 |
| 中间人 | 移除中间人（Remove Middle Man） |
| 拒绝继承 | 以委托取代继承（Replace Inheritance with Delegation） |

### 第三步：拆分为小步骤

将每个重构手法拆分为原子操作序列，每个步骤满足：

1. **单一操作**：一步只做一种重构（不混合提取方法和重命名）
2. **可验证**：每步完成后可以运行测试确认行为未变
3. **可回滚**：每步失败可以独立撤销，不影响其他步骤
4. **有序依赖**：标注步骤间的依赖关系（哪些可并行、哪些必须顺序）

### 第四步：输出重构计划

将分析结果写入 `docs/artifacts/refactoring-plan.md`，包含以下章节：

```markdown
# 重构计划

## 概要
- 重构目标：[一句话描述]
- 涉及范围：[文件/类列表]
- 预计步骤数：N

## 坏味道清单
[第一步的输出]

## 重构步骤
| 序号 | 操作 | 目标 | 验证方式 | 依赖 |
|------|------|------|----------|------|
| 1 | 提取方法 | OrderService.process() → extractValidation() | 单元测试全绿 | 无 |
| 2 | 搬移方法 | extractValidation() → OrderValidator | 单元测试全绿 | 步骤1 |
| ... | ... | ... | ... | ... |

## 风险评估
- [识别的风险和缓解措施]

## 不做的事情
- [明确排除的改动，防止范围蔓延]
```

## 约束

- 本技能为**只读分析**，不修改任何代码
- 输出的计划必须足够详细，让 `implementer` 无需额外判断即可逐步执行
- 如果坏味道涉及公共接口变更，必须标注为高风险并建议与用户确认
