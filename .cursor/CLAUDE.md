# 减少 LLM 常见编码错误的行为准则

> 根据需要与项目特定规则合并使用。
>
> 权衡取向：这些准则偏向**谨慎而非速度**。对于简单任务，可自行判断。

## 1. 先思考，再编码

不要假设。不要隐藏困惑。主动暴露权衡取舍。

实现之前：

- 明确陈述你的假设。如有不确定，先问。
- 如果存在多种理解方式，逐一列出——不要默默选一个。
- 如果有更简单的方案，说出来。必要时提出反对意见。
- 如果有不清楚的地方，停下来。指出困惑所在，然后提问。

## 2. 简洁优先

用最少的代码解决问题。不做投机性开发。

- 不实现未被要求的功能。
- 不为只用一次的代码做抽象。
- 不添加未被要求的"灵活性"或"可配置性"。
- 不为不可能发生的场景编写错误处理。
- 如果你写了 200 行但 50 行就能搞定，重写它。
- 自问："一个资深工程师会不会觉得这太复杂了？" 如果是，简化。

## 3. 精准修改

只动必须动的地方。只清理自己造成的问题。

编辑现有代码时：

- 不要顺手"改进"相邻的代码、注释或格式。
- 不要重构没有问题的代码。
- 须遵守 `.cursor/rules/` 已加载规范，不得因参考附近代码而忽略规则要求。
- 可匹配该文件既有缩进、换行等格式习惯。
- 如果发现无关的死代码，提一下——但不要删除它。

当你的改动产生了孤立代码时：

- 移除**因你的改动**而变得无用的 import、变量、函数。
- 除非被要求，不要移除已有的死代码。

检验标准：每一行改动都应直接追溯到用户的需求。

## 4. 目标驱动执行

定义成功标准。循环验证直到确认通过。

将任务转化为可验证的目标：

- "添加校验" → "为非法输入编写测试，然后让测试通过"
- "修复 bug" → "编写复现 bug 的测试，然后让测试通过"
- "重构 X" → "确保重构前后测试全部通过"

对于多步骤任务，列出简要计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强成功标准让你能独立循环推进。弱标准（"让它能跑"）则需要不断澄清。

---

**这些准则生效的标志：** diff 中不必要的改动更少，因过度复杂化导致的返工更少，澄清性提问出现在实现之前而非犯错之后。
